# VAW cross-project workshop/UX donor audit — 2026-10-19

**Status:** current research evidence, **not** an architecture decision, implementation authority, donor adoption, roadmap override, or Owner gameplay acceptance. Source observations below were verified on GitHub branches or the live Jaskinia browser during the 19 October investigation. A branch label is not a claim that it is accepted. Re-evaluate exact HEADs before applying a patch.

## Why this work exists

VAW has a technically supported `empty build → place/move/undo → attach Hull → Sandbox flight → return` path and a public Jaskinia entry. Recent source release: [`2681c383`](https://github.com/Jozzpoly/voxel-aeronautics-workshop/commit/2681c383489ad95913a0780589f15186b93320fd), release identity in [`gh-pages/BUILD_INFO.json`](https://github.com/Jozzpoly/voxel-aeronautics-workshop/blob/gh-pages/BUILD_INFO.json). Owner has **not** accepted editing ergonomics, flight feel, mechanical authoring, phone/touch controls, or polish. The core fantasy remains an open-ended machine sandbox with optional programming, direct piloting, understandable physical outcomes and fast build/test/rebuild—not a contract-menu simulator. Separate future explorations of Box3D/JV/ANVIL matter-first building must not force a VAW rewrite now.

The user requested donor archaeology beyond `main` and specifically regards Jaskinia as the current leading UI/UX laboratory, not as an immutable gold standard.

## Direct VAW source findings — require falsification, not automatic promotion to bug reports

1. **[Risk / high] concurrent edit loss.** `src/game/blueprint_controller.js` persists one `SAVE_KEY` payload and a single overwritten `SAVE_BACKUP_KEY` via `localStorage` after 220ms debounce. There is no evident per-tab revision/conflict check in that path. Two tabs at the same GitHub Pages origin can save different blueprints under the same key; old work may be displaced and the single backup slot may be displaced again. This is materially different from the tested, copy-preserving, v3-store approach of Jaskinia v6.3. **No real Owner loss observed**. Reproduce in *isolated* Chromium profiles with multiple tabs, not using existing Owner storage, before choosing solution.
2. **[Risk / medium] tool state vs import/reset.** `src/game/workshop_tool_mode.js` owns live Select mode; `src/game/blueprint_controller.js` `loadBlueprintData` and `newBlueprint` directly toggle `.tool-btn.active` based on `STATE.selectedBlock`, without synchronizing the mode controller. After Select→New/Load, the visual tool highlight may indicate BUILD while click handling stays in SELECT. The smoke currently proves entering/exiting Select via choosing a part, **not** this transition. Add the direct browser counterexample before a small fix.
3. **[UX hypothesis] camera framing and dominance of chrome.** The current VAW screenshot from the published build shows a small machine inside a huge grid, left/right panels and a full-width bottom palette. `camera_controller.js` supports orbit, pan, reset and flight follow, but does not visibly provide Owner-facing *frame selected / fit craft* analogous to JURE's dedicated Focus actions. Evaluate framing and task-focus before UI overhaul.
4. **[UX hypothesis] input semantics conflict.** Jaskinia's 3D viewer pan/orbit differ from VAW's `right-click=remove` and `middle/Alt=orbit`. An iframe can have its own controls; consistency matters to Owner muscle memory, but changing VAW destructive-click mapping without trials can be worse. Test context by context.
5. **[Core gap] editing linked parts.** `workshop_selection_controller.nudge` refuses any mechanically linked block. That's an honest limit, not a full manipulation workflow. JURE/JES/JV suggest separating selection, preview and one authored transaction, plus reasoned failure feedback, before tackling linked topology.
6. **[Observation gap] feedback provenance.** Jaskinia's `55-feedback.js` records selected project, window, device, timestamp and optional connected-apparatus state, and exports an Owner-controlled package. For a plain external VAW iframe, actual in-game design/test state must be verified rather than assumed to be recorded automatically.
7. **[Mobile not proven]** Native VAW pointer listeners currently return early on `pointerType === 'touch'`. Jaskinia can *launch* VAW on phone; that does not give it a working touch builder. Do not declare mobile acceptance or casually copy Jaskinia's touch map.

## Ranking after adversarial review

**P0 — protect the work:** audit VAW's save and restore behavior with two live tabs / reload / storage quota / older published build, in isolated disposable browser storage. If the overlap can destroy authored work, prioritize a small safe conflict/rescue boundary over cosmetic polish. Do not port Jaskinia's entire merge framework blindly.

**P1 — restore a trustworthy tool state:** targeted Select→New/Load/Undo/Flight→Return counterexamples, clear indicator of current mode, no accidental building/deleting. Source mismatch is visible already; confidence escalates with browser reproduction. Avoid restoring an agent mesh or redesigning all input.

**P2 — an actual pleasant correction:** focus/fit selection, preview drag/commit/cancel semantics with stable block IDs and one undo step, meaningful constrained/linked status. Qualify one action from Owner feel instead of implementing a huge gizmo suite.

**P3 — build and flight feel together:** assess relative object scale, camera rhythm, projection/texture treatment, feedback of contact/thrust/damage, and how the test result guides the next physical edit. Measure in real rendering and Owner trials. No broad aero retune before a meaningful hypothesis.

**P4 — Jaskinia/VAW continuity:** preserve existing one-click launch, focus, address and Owner-controlled feedback. Any additional agent instrumentation requires its own source/privacy/acceptance contract. No Jaskinia shell fork.

## First bounded trial and exit conditions

A disposable-profile trial should contain a real authored craft, a second tab with independent work, reload/return, Select then New/Load, building near an existing face, a physical flight then return, and a short Owner session focusing on *what feels wrong*. Capture exact source SHA, page URL, viewport, input device, selected action and expected/actual result; separate browser automation from Owner acceptance. A single reproduction should drive the smallest change, *followed* by both source and published-build gates.

**Rejection signals:** increased navigation cost, extra panels/shortcuts without better correction speed, loss of existing viable control paths, false visual feedback about persistent mode, one tab destroying another's work, camera change harming placement, or a correct isolated demo causing regression in whole-game feel. These veto copying any donor.

Do not expand to ANVIL-like matter properties, JV suspension, generic middleware, code-level Jaskinia imports or remote multiplayer at this stage.
